# Техническое задание VirtLite

**Версия 1.1 · 12.08.2026**

Приложение для macOS на Apple Silicon, создающее и запускающее виртуальные машины поверх
системного `Virtualization.framework`.

У каждого требования стабильный идентификатор. На них ссылаются issue, pull request'ы и коммиты.
Идентификаторы не переиспользуются: если требование отменено, его код уходит вместе с ним.

Приоритеты: **MVP** — этап 1, **v1** — до публичного релиза, **позже** — после.

---

## 1. Назначение и цели

### 1.1 Описание

VirtLite запускает Linux- и macOS-гостей на нативной скорости через `Virtualization.framework`.
Процессор не эмулируется: гость исполняется на том же ARM64-железе, что и хост.

### 1.2 Цели

- Лёгкий по весу и потреблению ресурсов инструмент для Linux-VM без десктоп-комбайнов.
- Нативная производительность за счёт системного фреймворка вместо эмуляции.
- Основной сценарий «выбрать образ → настроить → запустить» — четыре шага.
- Минимальный дисковый след: разреженные ASIF-образы.

### 1.3 Аудитория

Разработчики, которым нужна изолированная Linux-среда; студенты и мейкеры, изучающие Linux;
пользователи Mac, которым не подходят тяжёлые коммерческие решения.

### 1.4 Вне рамок

- **Windows-гости — невозможны на выбранном стеке.** `Virtualization.framework` поддерживает
  только Linux и macOS; формат образа тут ни при чём. Продукты, которые это умеют (UTM,
  Parallels), используют QEMU или собственный гипервизор поверх низкоуровневого
  `Hypervisor.framework`. Добавление Windows означает смену стека и отказ от цели 1.2 — другой
  проект. Решение зафиксировано.
- Порт под Windows как хост. SwiftUI там нет, «портированием» стало бы переписывание интерфейса.
- Гостевые x86_64-системы. Rosetta транслирует бинарники внутри ARM-гостя, не заменяет систему.
- Intel Mac в роли хоста.
- Оркестрация парка VM, удалённый доступ.
- CLI и headless — не в v1, но архитектура раздела 3 их не исключает.

## 2. Стек и зафиксированные решения

| Компонент | Решение | Обоснование |
|---|---|---|
| Язык | Swift 6 | Строгая конкурентность: весь VZ обязан вызываться со своей очереди |
| UI | SwiftUI + AppKit | AppKit там, где нужен `VZVirtualMachineView` |
| Виртуализация | `Virtualization.framework` | Единственный вариант без эмуляции |
| Минимальная macOS | **26.0** | ASIF и vmnet-топологии без веток `#available` |
| Архитектура | arm64 | — |
| Формат диска | **ASIF** | Разреженный, компактный, быстро переносится |
| Дистрибуция | GitHub Releases | Подписанный и нотаризованный `.dmg`, обновления через Sparkle |
| Лицензия | **Apache 2.0** | Permissive + patent grant |
| Bundle ID | `com.ispy4you.virtlite` | Участвует в подписи и путях к данным |

**О минимальной версии.** macOS 26.0 отсекает пользователей на 13–15. Сделка сознательная: ASIF и
`VZVmnetNetworkDeviceAttachment` появились в 26, а поддержка ранних версий означала бы две
параллельные ветки кода в дисковой подсистеме и сети на весь срок жизни проекта.

Оба основания подтверждены проверкой (см. [api-verification.md](api-verification.md)). ASIF:
8 ГБ образ занимает 4 МБ на диске. vmnet: сети создаются с обычным
`com.apple.security.virtualization`, ограниченное разрешение Apple не требуется.

**О дистрибуции.** Причина выбора GitHub вместо App Store — не «sandbox блокирует виртуализацию»:
entitlement `com.apple.security.virtualization` доступен любому разработчику. Причины реальные:
требования ревью App Store к приложениям, исполняющим произвольный гостевой код, и свобода в
работе с файлами пользователя. Формулировку подтвердить прототипом этапа 0.

## 5. Нефункциональные требования

### 5.1 Производительность

| ID | Требование | |
|---|---|---|
| `NFR-01` | Только системный фреймворк, никакой эмуляции | MVP |
| `NFR-02` | Энергопотребление измеряется на простое и под нагрузкой, фиксируется в отчёте перед релизом | v1 |
| `NFR-03` | Приложение без запущенных VM не потребляет заметного CPU | v1 |

### 5.2 Надёжность

Требование версии 1.0 «сохранять состояние VM при неожиданном завершении приложения» невыполнимо:
VM исполняется внутри процесса приложения. Заменено двумя достижимыми.

| ID | Требование | |
|---|---|---|
| `NFR-04` | Аварийное завершение не повреждает диски. Для гостя это отключение питания; целостность обеспечивает журналируемая ФС гостя, приложение отвечает за корректные режимы записи | MVP |
| `NFR-05` | Бандл помечается «грязным» на время работы; при следующем открытии — предупреждение о некорректном выключении | v1 |
| `NFR-06` | Понятно объясняются: нехватка места, недоступный образ, несовместимая архитектура, конфликт ресурсов, отсутствие Rosetta, неудачная загрузка шаблона | MVP |

## 7. Ограничения версии 1

Колонка «природа» — для команды: отделяет то, что закрывается работой, от того, что зависит от
Apple. Колонка «формулировка» — готовый текст для интерфейса и README.

| Ограничение | Природа | Формулировка для пользователя |
|---|---|---|
| Bridged networking | entitlement | Требует разрешения от Apple, выдаваемого индивидуально. Вместо него — проброс портов, который такого разрешения не требует и закрывает большинство задач |
| USB-аксессуары | macOS 27 | Полноценный проброс появляется в macOS 27 |
| Уменьшение диска | решение v1 | Диск можно увеличить или добавить новый. Уменьшить — нельзя |
| 3D-ускорение в Linux | платформа | Экран без аппаратного 3D; тяжёлые рабочие столы будут медленными |
| Только ARM64-гости | платформа | x86_64-системы не запускаются; Rosetta транслирует отдельные бинарники |
| Не более двух macOS-гостей | платформа | Системное ограничение Apple |
| Буфер обмена зависит от гостя | платформа | В Linux нужен `spice-vdagent`; с macOS-гостем — от macOS 15 с обеих сторон |
| Совместимость дистрибутивов | платформа | Зависит от virtio-драйверов и EFI-загрузки в образе |
| Windows-гости | платформа | Фреймворк запускает только Linux и macOS |
| Intel Mac | вне рамок | Только Apple Silicon |

## 8. Этапы

**Этап 0 — research (1–2 недели).** Сверить availability-аннотации в заголовках SDK; проверить
entitlements и подпись; прототип без UI — запуск Linux с `.iso` и выводом по serial; подтвердить
минимальную версию macOS.

**Этап 1 — MVP.** Все требования с меткой MVP. Разделение слоёв (`ARC-01`…`ARC-03`) закладывается
сразу — позже это рефакторинг всего проекта.

**Этап 2 — снапшоты и ресурсы.** `LC-05`…`LC-07`, `LC-10`, общие папки, буфер обмена, Rosetta,
проброс портов, консоль.

**Этап 3 — образы и гости.** Манифест шаблонов, дополнительные диски, увеличение диска, аудио,
macOS-гость.

**Этап 4 — перенос и полировка.** Экспорт, импорт, клонирование, локализация, доступность,
обработка краевых случаев.

**Этап 5 — релиз.** Производительность и энергопотребление, подпись, нотаризация, Sparkle,
документация, дисклеймер по товарным знакам.

## 10. Критерии приёмки MVP

- [ ] Linux VM создаётся из `.iso` ровно за четыре шага мастера (`VM-01`)
- [ ] VM запускается и даёт графический доступ к установщику, включая управление мышью (`HW-05`)
- [ ] Гость выходит в интернет через NAT без дополнительной настройки
- [ ] CPU и RAM применяются и сохраняются между запусками; границы совпадают с тем, что сообщает фреймворк
- [ ] После установки гость загружается с диска, а не снова с образа (`INS-01`)
- [ ] Удаление VM с подтверждением полностью очищает файлы бандла
- [ ] Приложение не падает при принудительной остановке во время установки; бандл остаётся пригодным
- [ ] x86_64-образ отклоняется до создания VM с объяснением (`VM-06`)
- [ ] Ядро собирается и проходит тесты без импорта `Virtualization` (`ARC-01`)
